# レース開始・終了通知仕様

`racing_kart_manager` が、レースの開始時刻と終了時刻を MQTT で通知する。

順位計算はしない。規定周回数・完走判定・中断時の扱いは順位計算側が持つ。このトピックが
伝えるのは**時刻だけ**である。

- 実装: `manager/racing_kart_manager_core.py`（純ロジック）、`manager/racing_kart_manager.py`
- テスト: `manager/tests/`（§6 の観点に対応する）
- joy と選択の意味: [`joy-routing.md`](joy-routing.md)

## 1. 接続先

| 項目 | 値 |
| --- | --- |
| ブローカ | `kart_telemetry` と同一（`racing_kart_interface` の `racing_kart_telemetry_uploader` が使うもの） |
| 接続情報 | `.env` の `MQTT_HOST` / `MQTT_PORT` / `MQTT_USERNAME` / `MQTT_PASSWORD` |
| クライアント | `mosquitto_pub`（`mosquitto-clients`） |

- **RN-01** 認証情報をリポジトリに置かない。`.env.example` にはブローカのホスト名とポートだけを書き、ユーザ名とパスワードは空にする。

## 2. トピック

| 用途 | トピック | QoS | retain |
| --- | --- | --- | --- |
| レース開始 | `kart_race_start` | 1 | true |
| レース終了 | `kart_race_finish` | 1 | true |

## 3. ペイロード

```json
{ "started_at": "2026-08-15T13:12:03.480+09:00" }
```

```json
{ "finished_at": "2026-08-15T13:12:03.480+09:00" }
```

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `started_at` | string (ISO 8601 / JST) | レース開始の時刻。オフセット `+09:00` を必ず明示する |
| `finished_at` | string (ISO 8601 / JST) | レース終了の時刻。オフセット `+09:00` を必ず明示する |

- **RN-02** 小数部はミリ秒3桁とする。
- **RN-03** オフセットは `+09:00` を明示する。`Z` や省略は認めない。

## 4. 発火条件

| 通知 | 条件 |
| --- | --- |
| `kart_race_start` | **全台選択**かつ **Y（AUTONOMOUS）押下**の立ち上がり、または GUI の**レース開始ボタン**の押下 |
| `kart_race_finish` | **緊急停止4種（LB / RB / START / BACK）のいずれか押下**の立ち上がり、または GUI の**レース終了ボタン**の押下 |

joy による条件と GUI のボタンは独立に見る。どちらでも同じトピックへ同じ形式で送る。

- **RN-04** 開始は Y のみで判定する。X（AUTONOMOUS_STEER_ONLY）では通知しない。
- **RN-05** どちらも**立ち上がり**で判定する。`joy_node` は押下中も 20Hz で送り続けるため、
  押されているかどうかだけで判定すると1回の押下で連続送信になる。
- **RN-06** レースの進行状態を持たない。条件が再び成立すればそのつど送る。開始を2回押せば
  `started_at` は2回とも送られ、retain は後のもので上書きされる。終了も同じで、
  レース中かどうかを問わず緊急停止のたびに送る。
- **RN-07** 2つの条件は独立に評価する。同時に成立していれば両方送る。
- **RN-08** 起動後に最初に受け取った joy では発火しない。前回値の初期化にだけ使う。
  ボタンを押したまま manager が起動したときに、押した覚えのない通知が飛ぶのを防ぐ。
- **RN-09** 時刻は受信した joy の `header.stamp` を使う。ボタンが押された時刻そのものであり、
  MQTT の接続や再試行にかかった時間が混じらない。
- **RN-10** 開始は、要素数が規定どおりの joy のときだけ判定する（`joy-routing.md` REQ-15）。
  終了は要素数を問わない。要素数の違う入力ではどの車両も操縦できない（REQ-18）のに、
  ボタン配列の違う機器の index 3 が偶然立ってレース開始が飛び、retain された
  `started_at` を上書きしてしまうのを防ぐ。止めるほうは壊れていても通す。
  GUI のボタンにこの制限は掛からない。指令の出どころが joy ではないため（REQ-36）。
- **RN-16** GUI のボタンによる通知は**押下1回につき1回**。一斉指令の繰り返し（REQ-33）では
  重複させない。各フレームで出すと、1回の押下で同じ時刻の通知が10回飛ぶ。
- **RN-17** GUI のボタンによる通知の時刻も、その指令を最初に乗せた joy の `header.stamp` を使う
  （RN-09 と同じ）。押下から最大1フレーム（20Hz で 50ms）遅れる。
  joy が届いていない間はボタンを押しても指令が乗らないため、通知も出ない。

## 5. 送信の扱い

- **RN-11** publish は joy の処理を止めない。別スレッドで行う。
- **RN-12** 失敗したら間隔をあけて最大2回まで再試行する。それでも送れなければログに残して諦める。
- **RN-13** 通知の成否は車両の操作に一切影響しない。ブローカに繋がらなくても joy の中継は続く。
- **RN-14** 通知の結果を GUI に出さない。ログで確認する。
- **RN-15** 認証情報は `mosquitto_pub` の引数として渡すため、publish の間だけ同じPCの
  他ユーザから `ps` で見える。`mosquitto_pub` に引数以外でパスワードを渡す手段が無い
  ことによる既知の制約で、会場の共用PCではそれを前提に扱う。

## 6. テスト観点

ROS を起動せず pytest だけで走る。純関数を検証する。

| ID | 観点 | 対応 |
| --- | --- | --- |
| T-23 | 全台選択で Y を押した瞬間に開始が1回だけ発火する | RN-05 |
| T-24 | Y を押し続けても2回目は発火しない | RN-05 |
| T-25 | 単車選択・未選択で Y を押しても発火しない | 発火条件 |
| T-26 | X を押しても発火しない | RN-04 |
| T-27 | 緊急停止4種それぞれの押下で終了が1回だけ発火する | RN-05 |
| T-28 | 緊急停止を押し続けても2回目は発火しない | RN-05 |
| T-29 | 離してもう一度押せば再び発火する | RN-06 |
| T-30 | 開始条件と終了条件が同時に成立したら両方発火する | RN-07 |
| T-31 | 最初の joy では発火しない（押しっぱなしで起動しても飛ばない） | RN-08 |
| T-32 | ペイロードが `+09:00` とミリ秒3桁の ISO 8601 になる | RN-02, RN-03 |
| T-33 | 時刻が joy の `header.stamp` から作られる | RN-09 |

| T-47 | GUI のボタンは押下1回につき1回だけ通知する（繰り返しでは出さない） | RN-16 |
| T-48 | 一斉指令とレース通知のイベントが対応する | §4 |
